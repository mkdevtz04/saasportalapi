# Architecture

## The pieces

| Piece | What it is | Where |
|---|---|---|
| Web app | Laravel: marketing page, ISP dashboard, agent POS, platform admin, customer portal, APIs | this repository |
| Database | MySQL. One database for everything, including the RADIUS tables | |
| Queue worker | Grants access after a payment, sends SMS receipts | `php artisan queue:work` |
| Scheduler | Reconciles payments, checks routers, cleans up | `php artisan schedule:run` every minute |
| FreeRADIUS | Logs customers in when a router asks | `deploy/freeradius/` |
| Router agent | A small script on each router that reports in every minute | generated by the setup command |
| PalmPesa | The mobile money gateway. One platform account collects every payment | outside |

## Tenants

Each ISP is a tenant. A tenant's portal lives on its own subdomain (`acme.wifikitaa.site`). Tenant data is
separated in the models: tenant-owned models filter every query to the tenant of the current request and stamp
new rows with it. This is on top of the explicit checks in controllers, so a forgotten check cannot leak
another ISP's rows. The platform admin panel, console commands and queue jobs see every tenant.

## The money rules

These are the rules the tests defend. Do not change one without changing the tests on purpose.

1. **The gateway is the only truth about a payment.** Callbacks and anything the browser sends are never
   trusted. The platform asks PalmPesa itself, using the order id stored on its own transaction row.
2. **A payment is settled exactly once.** The transaction is locked, its status changes and the tenant wallet
   is credited in one database transaction. A callback and a status poll racing each other cannot double credit.
3. **Only confirmed portal payments fill the tenant wallet.** Voucher redemptions and agent sales are cash the
   ISP collected offline. They are recorded for reports but never touch the wallet.
4. **Every movement of tenant money is in an append-only ledger.** `wallet_entries` rows are never edited or
   deleted, each movement has a unique reference so it can only apply once, and the wallet balance is a cached
   total that must equal the ledger.
5. **The platform fee is taken at withdrawal only.** No fee on portal payments, none on vouchers. The fee is
   stored on the withdrawal and counts as platform revenue when the admin marks it paid.
6. **A wallet can never hold more than portal payments explain.** `wallet:audit` and the admin
   reconciliation page check this and the ledger, and show the expected PalmPesa balance.

### Payment flow

```
customer picks a package      POST /api/payment/initiate   -> pending transaction + STK push
customer confirms on phone
gateway calls back            POST /api/payment/callback   -> only names the order, then we ask PalmPesa
portal polls                  GET  /api/payment/status     -> same check, by unguessable id
                                 |
                                 v
                    PaymentSettlement::settle  (locked, once)
                       status = completed, wallet credited, ledger entry
                       router in one-command mode: RADIUS login written in the same transaction
                       router in API mode:         access job queued, retried, status tracked
                       SMS receipt queued
```

`payments:reconcile` settles any paid order whose callback never arrived.

## Connecting routers

Routers used to be reached by the server, which cannot work when the router sits behind NAT. Now every router
connects **out**:

- **RADIUS.** The router asks FreeRADIUS whether a customer may log in. The app writes the login (`radcheck`,
  `radreply`) when a payment or voucher succeeds, including expiry, speed and data cap. Every login is tied to
  one ISP by a `NAS-Identifier` condition, so it cannot be used on another ISP's routers. A returning device gets
  its own login by MAC address so it reconnects without typing anything.
- **Router agent.** A script scheduled on the router calls `/api/agent/{token}/poll` every minute. That is the
  heartbeat (online, RouterOS version, customers connected) and how the platform sends commands (reboot,
  disconnect a customer). Commands are a fixed whitelist and every value in them is escaped.
- **Setup.** One pasted command downloads a script that sets the router identity, the RADIUS server, the hotspot
  profile, the walled garden, a branded login page and the agent. Every step reports its own failure.

Routers connected the old way (the platform logs in over the API, optionally through `mikrotik-agent.php`) still
work and can be switched to the new setup from the router page. New routers use the new setup.

### Known limits

- All routers share one RADIUS secret, because routers behind carrier NAT have no stable address to identify
  them. The `NAS-Identifier` condition is what separates ISPs. Treat the secret like a password.
- The first download of the setup script does not verify the server certificate, because RouterOS has no
  certificate authorities installed by default. The secret provision token protects that step.
- Cutting a customer off happens within a minute (through the agent), not instantly, because RADIUS
  disconnect messages cannot reach a router behind NAT.

## Security model

- Sign-in for tenants and platform admins is throttled per address and per account, with an audit trail.
- Money and access actions are recorded in an append-only audit log (who, what, which ISP, from where).
- Platform support can open an ISP dashboard. It is marked on screen, recorded, and withdrawals and payout
  changes are blocked while it lasts.
- Router setup scripts are built with escaping for every value a tenant can influence, and use the configured
  address, never the request's Host header.
- The portal only accepts a local router address as the place to send a customer's WiFi login.
- Public endpoints that could be guessed at are rate limited: voucher redemption, sign-up, setup downloads,
  payment prompts per phone number, and the router agent per router.

## What is and is not verified

Automated tests cover the Laravel side: payments, the ledger, tenant isolation, scripts, RADIUS rows, agent
commands, the portal, SMS receipts, reports, reconciliation, audit and hardening.

**Not verified, because it needs real infrastructure that was not available while this was built:**

- FreeRADIUS reading the rows and answering routers. Follow `deploy/freeradius/README.md` on a staging server.
- The generated RouterOS script and agent on a real router. Try one RouterOS v6 and one v7 router before rollout.
- The Beem SMS integration against the real service.
- Behaviour under load. `deploy/loadtest/portal.k6.js` is a starting point.

## Not built

- Subscriptions and invoices. The platform is free, by decision.
- Two-factor sign-in for the platform admin. Recommended before real money flows.
- Filament, Horizon and Redis from the original plan. The database queue and plain Blade views are used instead.
